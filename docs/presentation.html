Context & Motivation

The Retail Stationery Problem

Real-World Pain Points
📉
Untracked Stock-Outs & Surges
Stationery stores manage hundreds of low-cost SKUs (pens, notebooks, adhesives). Back-to-school and exam surges trigger stock-outs because storekeepers lack automated reorder alerts.
📓
Manual Register Inaccuracies
Paper-based stock ledgers suffer from human calculation mistakes, delayed recording, and inventory shrinkage (unaccounted missing items or damage).
⚠️
Overselling & Negative Inventory
Uncoordinated sales desks sell items that are physically out of stock, leading to billing discrepancies and customer dissatisfaction.
💰
Blind Financial Valuation
Store owners cannot answer simple business questions in real-time: "What is the total capital tied up in my shop right now?" or "Which category has excess dead stock?"
Viva Speaker Note: "Stationery retail is unique because unit margins are small but SKU volume is high. If a student needs a specific geometry set and it's out of stock, the store loses immediate revenue. Our system eliminates these blind spots."

Data Modeling

Normalized Relational Schema (3NF)

5 Relational Tables
Table Primary Key Foreign Keys & Relationships Role & Constraints
categories category_id 1-to-Many with products Categorizes items (Pens, Notebooks, Markers). Unique category name.
suppliers supplier_id 1-to-Many with products Maintains supplier contact info, phone, and address.
products product_id FKs: category_id, supplier_id Unique SKU & Barcode; CHECK (quantity >= 0); unit_price > 0.
stock_transactions transaction_id FK: product_id Immutable audit trail: INWARD, OUTWARD, DAMAGED.
sales sale_id FK: product_id Records POS billing: quantity sold, total price, and auto-generated timestamp.
Viva Speaker Note: "The database is strictly in 3rd Normal Form. Redundancy is eliminated. The stock_transactions table acts as an immutable append-only ledger so every adjustment or damage write-off is permanently auditable."
Business Logic

Mathematical Rules & Real-Time KPIs

Automated Decisions
1. Dynamic Stock Status
if (quantity == 0) → OUT OF STOCK
else if (qty ≤ reorder) → LOW STOCK
else → IN STOCK
Evaluated dynamically on every query. Never hardcoded, ensuring instant UI badge transitions when sales or deliveries occur.
2. Suggested Reorder Quantity
ReorderQty =
MAX(0, (ReorderPoint × 2) - Qty)
Takes the guesswork out of purchasing. Instantly informs the storekeeper how many units to purchase to safely restore a 2× buffer.
3. Real-Time Valuation
CategoryValuation =
∑ (ProductQty × UnitPrice)
Aggregated live across the entire catalog and segmented by category to provide instant business intelligence to the store owner.
Viva Speaker Note: "Examiners frequently ask how we calculate the reorder quantity. We use the standard retail buffer formula: (Reorder Point × 2) - Current Quantity. If a product has a threshold of 10 and we have 4 units left, the system suggests ordering (20 - 4) = 16 units."
Concurrency & Reliability

Atomic POS Sales & ACID Guarantees

ACID Compliant
Atomic 3-Way POS Sale Operation
When a cashier clicks Complete Sale:
  1. conn.setAutoCommit(false);
  2. Verify current stock ≥ requested quantity.
  3. Deduct product quantity: UPDATE products SET quantity = quantity - ?
  4. Write audit entry: INSERT INTO stock_transactions(..., 'OUTWARD')
  5. Write sales entry: INSERT INTO sales(...)
  6. conn.commit();
Fail-Safe Exception Handling & Rollback
try {
  conn.setAutoCommit(false);
  // Execute 3 atomic statements...
  conn.commit();
} catch (Exception e) {
  conn.rollback(); // Restores clean state
  throw new IllegalStateException("Sale failed");
}
Zero ghost sales, zero missing audit logs, and zero negative stock discrepancies.
Viva Speaker Note: "We guarantee ACID properties. If the database crashes or an error occurs during step 4, the rollback() method reverses all changes. The inventory is never decremented unless the sale is also permanently recorded."

Quality Engineering

10 Robust Edge Cases Handled

Zero Blindspots
Input & Security Validations
• Duplicate SKU: Rejected with 409 Conflict.
• SQL Injection: Blocked 100% via PreparedStatement.
• Negative Prices: Guarded (unit_price > 0).

• Zero Sales Quantity: Rejected with 400 Bad Request.
• Financial Precision: Handled with double-precision arithmetic.

Academic Defense

Examiner Viva Q&A Cheat Sheet

Key Defenses
Q1: Why plain JDBC instead of Hibernate / JPA?
"ORM frameworks abstract away SQL queries and transaction management. In an academic project, writing plain JDBC proves understanding of PreparedStatement lifecycle, SQL optimization, and explicit commit/rollback controls."
Q2: How do you prevent SQL injection?
"Every parameter is bound using PreparedStatement.setObject(). The SQL statement is compiled before values are injected as literal data, making SQL injection mathematically impossible."
Q3: How do you handle simultaneous sales?
"We use MySQL InnoDB row-level locking during atomic updates and verify the stock count inside an active transaction. If stock is insufficient, the transaction rolls back cleanly."
Q4: Why Java 21 Virtual Threads?
"Java 21 Virtual Threads provide lightweight concurrency with minimal memory overhead, allowing our embedded HTTP server to handle high concurrent POS traffic effortlessly."
